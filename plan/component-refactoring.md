## B. コンポーネント志向を阻んでいる構造

ここからが本題です。**CSS より根が深い問題**が 5 つあります。

### B-1. 翻訳がクライアント専用のフック 【最大の障害】

`useT()` が **56 ファイル**で使われています。`useState`(50) より多い。

```
useT      56    ← 翻訳
useState  50
useEffect 41
useLang   39    ← 表示言語
useAuth   32
```

`useT` は `useContext` を使うため、**文字を表示するだけの部品も client component
にせざるを得ません。** これが「119 中 79 が client」の最大の理由です。

**ただし、道は既に通っています。** `src/lib/serverLanguage.ts` に
`getRequestLanguage()` があり、Cookie（`neon_lang`）から言語を読めます。
`LanguageContext` はこの Cookie を書いています。つまり:

- サーバー側で `getRequestLanguage()` → `translations[lang]` を直接引ける
- 今はメタデータ生成にしか使われていない

**さらに悪いことに、`i18n.ts` の 1 行目に `"use client"` が付いていました。**
つまり 1,390 行の辞書（日本語＋英語の全文言）が、
- サーバー側から読めない
- ブラウザに丸ごと送られる

という状態でした。

### 実証済み（2026-08-04 に検証）

この節の主張は机上の空論ではなく、**実際に動かして確かめました。**

やったこと:

1. 辞書を `lib/i18nDictionary.ts` に分離（`"use client"` を付けない）
   - `i18n.ts` は今までどおり再輸出するので、**既存 56 ファイルの import は無変更**
   - `i18n.ts` は 1,449 行 → **68 行**
2. `lib/i18nServer.ts` に `getT()` を追加（Cookie から言語を読み、同じ辞書を引く）
3. `/about` を `"use client"` なしのサーバーコンポーネントに書き換え

確かめた結果:

| 確認 | 結果 |
| --- | --- |
| 型チェック | 通過 |
| テスト 383 件 | 全パス（about のテストはサーバー版に書き換え） |
| 画面表示 | 正常（HTML に本文が入っている） |
| **AboutContent 固有の文字列がクライアント JS に含まれるか** | **含まれない＝真のサーバーコンポーネント** |

**この方式は成立します。** 残り 55 ファイルにも同じ手が使えます。

**やること**: 表示するだけの部品から順に `getT()` へ移す。
言語切替ボタンなど、操作がある部分は client のままでよい。

**注意点 1**: 言語切替が `localStorage` と Cookie の二重管理になっていました。
→ **F-1 で Cookie に一本化済み（2026-08-04）**。

**注意点 2**: 辞書を分離しただけでは、ブラウザに送られる量は減りません。
`layout.tsx` と `error.tsx` を含む他の client 部品がまだ `useT` を使っているためです。
**送信量が減るのは、それらを移し終えたときです。**

### B-2. データ取得が画面の中にある

29 ファイルが `useEffect` の中で API を呼んでいます。順番はこうです。

```
ページを開く → 空の画面が出る → JavaScript が動く → データを取りに行く → やっと中身が出る
```

標準的な形はサーバー側で取ってから返すことです。ただし**このプロジェクトは
バックエンドが別（Django）**なので、単純ではありません。

障害になるのは認証です。実際の作りを調べた結果:

| 項目 | 現状 |
| --- | --- |
| 認証方式 | JWT を **HTTP-only Cookie**（`access_token` / `refresh_token`）で保持 |
| Cookie 設定元 | Django（`backend/users/views.py` の `_set_auth_cookies`） |
| SameSite | `Lax`、本番は `secure` 有効 |
| API 経路 | `next.config.ts` の `rewrites` で `/api/*` → Django |
| 期限切れの更新 | **ブラウザ側**で 401 を受けて `/api/auth/token/refresh/` を叩く |
| `middleware.ts` | **なし** |

**良い知らせ**: HTTP-only Cookie なので、Next.js のサーバー側から
`cookies()` で読んで Django へ転送できます。方式としては素直です。

**必ず詰まる点**: トークンの更新です。

- いまは「401 を受けたら refresh して新しい Cookie を受け取る」を**ブラウザ側**でやっている
- **サーバーコンポーネントは Cookie を書けません**（読むことしかできない）
- つまりサーバー描画中にトークンが切れていると、その場で更新できず 401 のまま

**これは Next.js の仕様なので、回避ではなく設計で解く必要があります。**
標準的な解き方は `middleware.ts` です。middleware は Cookie を書けるので、
「リクエストが来たら、期限が近ければ先に更新しておく」という役割を担わせます。

**やること（順番が重要）**:

1. `middleware.ts` を作り、トークン更新をここに移す
2. サーバー用の API クライアント（`cookies()` を読んで Django へ転送する版）を作る
3. その上でページをサーバー描画へ移す

**1 を飛ばして 2 から入ると、ログイン中のユーザーがときどき
ログアウト状態に見える**という、再現しにくい不具合になります。

### B-3. page.tsx が巨大で、部品に分かれていない

`app/translations/[id]/page.tsx` は **1,785 行**、その中に
**`useState` が 51 個**あります。実質ひとつの巨大な部品です。

35 ページ中 11 ページが 300 行を超えています。`settings/page.tsx` は 1 ファイルに
部品を 7 つ内包しています。

**やること**: 大きい順に、画面の中の意味のかたまりを `components/` へ切り出す。
このとき A-2（コピーされた定数）を先に潰しておかないと、コピーが増えます。

### B-4. 「読み込み中 / エラー / 空」の分岐が 34 ファイルで手書き

```
SkeletonList     76 箇所
<ErrorState      26 箇所
<EmptyState      13 箇所
useLoadMore      22 箇所
```

部品自体は用意されているのに、**組み合わせ方が画面ごとに手書き**です。
同じ 3 分岐を 34 回書いています。

**やること**: 「読み込み中ならこれ、失敗ならこれ、空ならこれ、あれば中身」を
まとめて引き受ける部品（例: `<AsyncList>`）を 1 つ作る。

### B-5. 一覧画面 4 枚が同じ骨格の手書き

`qa` / `articles` / `plans` / `translations` の 4 画面が、
**「見出し＋絞り込み＋2 カラムのカード一覧」**という同じ骨格を各自で書いています。
`columnStyle` `countBadgeStyle` のコピー（A-2）もここから来ています。

**やること**: 骨格を 1 つの部品にし、中身（カードの描き方・データの取り方）だけを
差し替えられるようにする。

## D. 進め方の提案

依存関係があるので、順番が重要です。

```
段階 0  翻訳をサーバーでも引けるようにする（B-1）        ← 済（2026-08-04）
          ↓
段階 1  ファイルをまたいだコピー定数を潰す（A-2）        ← 済（2026-08-04）
          ↓ ここを終えないと、切り出した先にコピーが増える
段階 2  共通の骨格部品を作る（B-4 / B-5）
          ↓ 見た目と分岐が揃ってから中身を動かす
段階 3  巨大な page.tsx を部品に割る（B-3）＋ CSS の残り（A-1）
          ↓ 同じファイルを触るので続けてやる（コミットは分ける）
段階 4  操作の無い部品をサーバーへ移す（B-1 の続き）
          ↓ ここまでデータの取り方は変えない
          ↓ ここで F-2「全ページへ広げるか」を再判断する
段階 5  middleware.ts でトークン更新を引き取る（B-2 の前提）
          ↓ ★ ここから認証に触る
段階 6  サーバー用 API クライアント → ページ単位でサーバー描画へ
          ↓
段階 7  error.tsx の拡充（C）※ Server Actions は F-3 により対象外
```

### なぜこの順番か

- **段階 0 を最初にやった理由**: 部品を切り出すときに「これは server にできるか」を
  判断できる状態にしておくためです。あとから全部品を見直すのは二度手間になります。
  実際にやってみて成立することも確認済みです（B-1 参照）
- **段階 1 〜 4 は見た目もデータの流れも変えません。** 構造を整えるだけなので、
  失敗しても影響が限定的です
- **段階 5 で初めて認証に触ります。** サーバーコンポーネントは Cookie を書けないため、
  トークン更新を middleware に移すのが先です。ここを飛ばすと、
  ログイン中なのにログアウト状態に見える不具合が出ます
- 段階 6 まで来ると、初回表示が実際に速くなります

### 各段階の重さ

| 段階 | 対象 | リスク | テストで守れるか |
| --- | --- | --- | --- |
| 0 | i18n + 読み物 5 枚 | 低 | ✅ 済 |
| 1 | 定数 9 種 | 低 | ✅ 済 |
| 2 | 一覧 4 枚 + 分岐 34 箇所 | 中 | ✅ 既存テストが効く |
| 3 | 大きい page 11 枚 | 中 | ✅ 既存テストが効く |
| 4 | client 部品の棚卸し | 中 | ✅ |
| 5 | middleware（認証） | **高** | ⚠️ e2e を足すべき |
| 6 | サーバー描画への移行 | **高** | ⚠️ e2e を足すべき |
| 7 | error.tsx の拡充 | 低 | ✅ |

段階 4 までは既存のテスト（383 件）と型チェックで守られた範囲です。
**段階 5 以降に進む前に、ログイン状態に関する e2e テストを足すべき**です。
現在 e2e に `auth.spec.ts` はありますが、「サーバー描画時にログイン状態が
正しく反映されるか」は対象外です。

### 段階 6・7 の記録 【2026-08-07】

読み物系の画面をサーバー描画へ移し終えました。移した画面は次のとおりです。

| 画面 | 何が変わったか | ブラウザ側に残したもの |
| --- | --- | --- |
| `/`（表紙） | 3 本の通信をサーバーでまとめる | なし（丸ごとサーバー） |
| `/read` | 本棚をサーバーで取る | 探すところ・続きから読む |
| `/articles` | 1 ページ目をサーバーで取る | もっと見る |
| `/plans` | 3 種類の一覧をサーバーで取る | なし |
| `/qa` | 2 列ぶんをサーバーで取る | 絞り込み・もっと見る・投稿 |
| `/qa/[id]` | 質問と回答をサーバーで取る | 書き直す・答える |
| `/translations` | 3 列ぶんをサーバーで取る | 検索・ページ送り・列切替 |
| `/[book]/[chapter]` | 本文をサーバーで取る | 節選択・お気に入り・コメント |

**通した考え方**

- **画面の状態は URL に置く。** 絞り込み・ページ番号・「質問する」を開いているか。
  画面の中に覚えさせると、サーバーが組み立て直すたびに食い違いが起きるうえ、
  その状態の URL を人に渡せません
- **一覧は 1 ページ目だけサーバーが取り、続きはブラウザが読み足す。**
  `useLoadMore(fetchPage, initial)` の `initial` がその受け渡し口です
- **取れなかったものは列や欄ごとに受け止める。** 1 つ落ちても他は出します。
  やり直しは `<RetryButton>`（`router.refresh()`）に統一しました

**詰まった点と、その解き方**

1. `"use client"` が付いたファイルはサーバーから読めない。
   `lib/i18n.ts`（文字の組み立て）と `lib/bookCatalog.ts`（書のカタログ）が
   これに当たったので、**計算だけの部分を別ファイルへ出して**（`i18nFormat.ts` /
   `bookCatalog.ts`）、フックのほうを `hooks/` へ移しました。既存の import は
   再輸出で今までどおり動きます
2. **「どの訳で読むか」がブラウザの控え（localStorage）にあった。**
   サーバーから読めないので、どの訳の本文を取ればよいか分かりませんでした。
   表示言語（F-1）と同じく Cookie（`neon_translation`）へ移しています。
   以前の控えが残っている人は初回だけ Cookie へ写して読み直します
3. 段階 5（`proxy.ts` でのトークン更新）は済んでいたため、ログインが要る
   データもサーバー側から取れました

**段階 7（error.tsx）**: 区画ごとの受け皿を 12 → 17 に増やしました
（`/login` `/register` `/forgot-password` `/reset-password` `/feedback`）。
併せて `loading.tsx` を `/plans` と `/qa/[id]` に足しています。

**残っているもの**: ログインが要る画面（`/bookmarks` `/profile` `/settings`
`/notifications`）と書き込む画面（`/articles/new` `/plans/new` `/login` など）は
client のまま据え置きです。`/translations/[id]`（1,785 行）は段階 3 の続きで、
サーバー描画の前に部品へ割るのが先です。

## E. コンポーネント志向にする際に気をつけること

洗い出しの中で見つかった、**切り出すときに壊しやすい点**です。

### E-1. 認証状態を前提にした部品は再利用できない

`router.push("/login")` が 5 ファイルに直接書かれています。
このまま部品に切り出すと「ログインしていなければ勝手に飛ぶ部品」ができてしまい、
別の場所で使えません。

**対処**: 認証ガードは画面（page / layout）の責任にし、部品は
「表示するデータ」だけを受け取る形にする。将来的には middleware に寄せる。

### E-2. 部品が Context に直接手を伸ばしている

`useAuth` が 32 ファイル、`useLang` が 39 ファイルで使われています。
部品の中から Context を読むと、その部品は**その Context がある場所でしか動きません**。
テストのたびにモックが必要になるのも同じ理由です
（現に `AboutContent.test.tsx` は Context のモックが要りました）。

**対処**: 葉の部品は props で受け取る。Context を読むのは画面に近い層だけにする。

### E-3. 1 ファイルに部品を詰め込むと再利用されない

`settings/page.tsx` は 1 ファイルに部品を 7 つ持っています。
ファイルの外から使えないので、同じものが他の画面で書き直されます。
`columnStyle` のコピー（A-2）はまさにこの結果です。

**対処**: 2 回以上使う見込みのある部品は `components/` に出す。

### E-4. 「1 画面 1 コンポーネント」に割らない

巨大な page を機械的に 3 分割しても、意味の切れ目でなければ読みやすくなりません。
`translations/[id]/page.tsx` の `useState` 51 個は、
**画面の中に複数の関心事（一覧・編集・コメント・進捗）が同居している**ことの表れです。

**対処**: 状態の使われ方でグループを見つけ、その単位で切り出す。
先に状態を整理してから部品にする。

## F. 着手前の決めごと 【2026-08-04 決定済み】

### F-1. 言語の正は **Cookie**（`neon_lang`）

localStorage は使いません。決めた理由と、決める前の実態:

- `layout.tsx` は既に Cookie から `initialLang` を渡していた
- ところが `LanguageContext` が起動直後に `localStorage` の値で上書きしていた
- `apiClient.ts` のエラー文言も localStorage を見ていた
- → **サーバーが描いた文字とブラウザの表示が食い違いうる**状態だった

**対応済み（このコミット）**:

| ファイル | 変更 |
| --- | --- |
| `contexts/LanguageContext.tsx` | localStorage の読み書きを削除。Cookie だけを書く |
| `lib/apiClient.ts` | 言語の判定を `document.cookie` へ変更 |
| `contexts/LanguageContext.test.tsx` | 新規（4 件） |

利用者から見た変化はありません。既存利用者の Cookie は、以前から
`LanguageContext` が毎回書いていたため既に存在します。

### F-2. サーバー描画は **読み物系から**

`/read` `/about` `/articles` など、ログインが要らない画面を先にサーバー描画へ移します。
全ページへ広げるかは、段階 4 まで終えてから改めて判断します。

**この決定の効果**: 段階 5（middleware での認証トークン更新）を後回しにできます。
リスクの高い作業に入る前に、初回表示の改善を出せます。

### F-3. Server Actions は **使わない**

Django が API を持っているため、フォーム送信は今までどおり `apiClient` 経由にします。
経路が一本のままなので、「どこを見れば送信処理が分かるか」が変わりません。
段階 7 の「Server Actions」は計画から外し、`error.tsx` の拡充のみ残します。
