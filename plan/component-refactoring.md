# コンポーネント志向への移行 — 洗い出し

作成: 2026-08-04 / 対象: frontend

このドキュメントは「Next.js の標準的なコンポーネント志向に書き換える」ために、
**いま何が足りていないか**を実測で洗い出したものです。作業計画そのものではなく、
判断材料です。実際に着手するときは、ここから段階ごとの計画を切り出します。

デザイン（CSS）側の決定版は `plan/design-refactoring.md` です。重複しないよう、
ここでは「コンポーネント志向のために CSS 側でやり残していること」だけを扱います。

## A. CSS 側でやり残していること

デザインの共通化はほぼ終わっていますが、**コンポーネント化の障害になる部分**が残っています。

### A-1. インライン指定 212 箇所

内訳（`plan/design-refactoring.md` の調査より）:

- **状態で変わるもの 67**（`active ? アクセント : 灰`）
  → クラスの付け外しに変える。これは共通部品を作るときに必ず通る作業
- **位置と効果 53**（`zIndex` `top/left` `transform` `backdropFilter` `transition`）
  → 共通化しない。その部品の `.module.css` に置くのが正しい
- **残り**（1 つ変な宣言があるせいで丸ごと残ったもの）

### A-2. ファイルをまたいでコピーされたスタイル定数 10 種

**同じ名前・同じ中身**が複数ファイルに定義されています。コンポーネントを切り出す前に

## B. コンポーネント志向を阻んでいる構造

ここからが本題です。**CSS より根が深い問題**が 5 つあります。

### B-1. 翻訳がクライアント専用のフック 【最大の障害】

`useT()` が **56 ファイル**で使われています。`useState`(50) より多い。

```
useT      56    ← 翻訳
useState  50
useEffect 41
useLang   39    ← 表示言語
useAuth   32
```

`useT` は `useContext` を使うため、**文字を表示するだけの部品も client component
にせざるを得ません。** これが「119 中 79 が client」の最大の理由です。

**ただし、道は既に通っています。** `src/lib/serverLanguage.ts` に
`getRequestLanguage()` があり、Cookie（`neon_lang`）から言語を読めます。
`LanguageContext` はこの Cookie を書いています。つまり:

- サーバー側で `getRequestLanguage()` → `translations[lang]` を直接引ける
- 今はメタデータ生成にしか使われていない

**さらに悪いことに、`i18n.ts` の 1 行目に `"use client"` が付いていました。**
つまり 1,390 行の辞書（日本語＋英語の全文言）が、
- サーバー側から読めない
- ブラウザに丸ごと送られる

という状態でした。

### 実証済み（2026-08-04 に検証）

この節の主張は机上の空論ではなく、**実際に動かして確かめました。**

やったこと:

1. 辞書を `lib/i18nDictionary.ts` に分離（`"use client"` を付けない）
   - `i18n.ts` は今までどおり再輸出するので、**既存 56 ファイルの import は無変更**
   - `i18n.ts` は 1,449 行 → **68 行**
2. `lib/i18nServer.ts` に `getT()` を追加（Cookie から言語を読み、同じ辞書を引く）
3. `/about` を `"use client"` なしのサーバーコンポーネントに書き換え

確かめた結果:

| 確認 | 結果 |
| --- | --- |
| 型チェック | 通過 |
| テスト 383 件 | 全パス（about のテストはサーバー版に書き換え） |
| 画面表示 | 正常（HTML に本文が入っている） |
| **AboutContent 固有の文字列がクライアント JS に含まれるか** | **含まれない＝真のサーバーコンポーネント** |

**この方式は成立します。** 残り 55 ファイルにも同じ手が使えます。

**やること**: 表示するだけの部品から順に `getT()` へ移す。
言語切替ボタンなど、操作がある部分は client のままでよい。

**注意点 1**: 言語切替が `localStorage` と Cookie の二重管理になっています。
サーバー側は Cookie しか読めないため、**Cookie を正とする**よう整理が必要です。

**注意点 2**: 辞書を分離しただけでは、ブラウザに送られる量は減りません。
`layout.tsx` と `error.tsx` を含む他の client 部品がまだ `useT` を使っているためです。
**送信量が減るのは、それらを移し終えたときです。**

### B-2. データ取得が画面の中にある

29 ファイルが `useEffect` の中で API を呼んでいます。順番はこうです。

```
ページを開く → 空の画面が出る → JavaScript が動く → データを取りに行く → やっと中身が出る
```

標準的な形はサーバー側で取ってから返すことです。ただし**このプロジェクトは
バックエンドが別（Django）**なので、単純ではありません。

障害になるのは認証です。

- 認証は Cookie（JWT）で、`credentials: "include"` を付けてブラウザから直接投げている
- `next.config.ts` の `rewrites` で `/api/*` を Django に転送している
- サーバー component から Django を呼ぶには、**受け取った Cookie を手で転送する**必要がある
- `middleware.ts` は無い

**やること**: サーバー側用の API クライアント（Cookie を転送する版）を用意する。
これは認証に触るので、単独の段階として慎重に進めるべきです。

### B-3. page.tsx が巨大で、部品に分かれていない

`app/translations/[id]/page.tsx` は **1,785 行**、その中に
**`useState` が 51 個**あります。実質ひとつの巨大な部品です。

35 ページ中 11 ページが 300 行を超えています。`settings/page.tsx` は 1 ファイルに
部品を 7 つ内包しています。

**やること**: 大きい順に、画面の中の意味のかたまりを `components/` へ切り出す。
このとき A-2（コピーされた定数）を先に潰しておかないと、コピーが増えます。

### B-4. 「読み込み中 / エラー / 空」の分岐が 34 ファイルで手書き

```
SkeletonList     76 箇所
<ErrorState      26 箇所
<EmptyState      13 箇所
useLoadMore      22 箇所
```

部品自体は用意されているのに、**組み合わせ方が画面ごとに手書き**です。
同じ 3 分岐を 34 回書いています。

**やること**: 「読み込み中ならこれ、失敗ならこれ、空ならこれ、あれば中身」を
まとめて引き受ける部品（例: `<AsyncList>`）を 1 つ作る。

### B-5. 一覧画面 4 枚が同じ骨格の手書き

`qa` / `articles` / `plans` / `translations` の 4 画面が、
**「見出し＋絞り込み＋2 カラムのカード一覧」**という同じ骨格を各自で書いています。
`columnStyle` `countBadgeStyle` のコピー（A-2）もここから来ています。

**やること**: 骨格を 1 つの部品にし、中身（カードの描き方・データの取り方）だけを
差し替えられるようにする。

## C. Next.js の作法として足りないもの

| 項目 | 現状 | 標準的な姿 |
| --- | --- | --- |
| `error.tsx` | 1 個だけ | 主要な区画ごとに置く（今は 1 画面のエラーが全体に波及しうる） |
| `loading.tsx` | 7 個 | サーバー側で取るようになったら各ルートに |
| Server Actions | 0 | 投稿・編集・削除はこれで書くのが標準 |
| Route Handlers | 0 | OAuth コールバックなど、サーバー側で処理したいものに |
| `middleware.ts` | なし | 未ログイン時のリダイレクトを一元化できる |
| 認証ガード | 各画面で `useEffect` → `router.push` | middleware か layout で |

とくに**認証ガードが 29 ファイルに散っている**のは、コンポーネント志向にする際の
地雷です。切り出した部品が「ログイン状態を知っている前提」になっていると、
再利用できません。

## D. 進め方の提案

依存関係があるので、順番が重要です。

```
段階 1  CSS の残り（A-1 / A-2 / A-3）
          ↓ ここを終えないと、切り出した先にコピーが増える
段階 2  翻訳をサーバーでも引けるようにする（B-1）
          ↓ ここを終えないと、部品が全部 client のまま
段階 3  共通の骨格部品を作る（B-4 / B-5）
          ↓ 見た目と分岐が揃ってから中身を動かす
段階 4  巨大な page.tsx を部品に割る（B-3）
          ↓ ここまでは client のままでよい。構造だけ整える
段階 5  サーバー側 API クライアントと認証の転送（B-2）
          ↓ 認証に触るので単独で
段階 6  ページ単位でサーバー描画へ移す
段階 7  Server Actions・middleware・error.tsx（C）
```

### なぜこの順番か

- **段階 1 〜 4 は見た目もデータの流れも変えません。** 構造を整えるだけなので、
  失敗しても影響が限定的です
- **段階 5 で初めて認証に触ります。** ここが唯一、本番で壊れると痛い部分なので、
  それまでの段階で足場を固めておきます
- 段階 2 を先にやる理由は、**部品を切り出すときに「これは server にできるか」を
  判断できる状態にしておく**ためです。あとから全部品を見直すのは二度手間になります

### 段階 1 〜 4 の目安

いずれも既存のテスト（383 件）と型チェックで守られた範囲の作業です。
段階 5 以降は、e2e テストを足してから進めるべきです。

---

## E. 着手前に決めておきたいこと

1. **言語の正をどちらにするか**（Cookie か localStorage か）
   → サーバーで引くなら Cookie が正。切替時の挙動が少し変わります
2. **サーバー描画をどこまで広げるか**
   → 全ページか、読み物系（`/read` `/about` `/articles`）だけか。
   後者なら認証の転送を後回しにできます
3. **Server Actions を使うか**
   → Django が API を持っているので、必須ではありません。
   使うと form の扱いが素直になりますが、経路が二本になります
