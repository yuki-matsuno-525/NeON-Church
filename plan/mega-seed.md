# 本番確認用 特大シードデータ計画（seed_demo）

本番で目視確認するために、「たくさんの人に使い込まれている」状態を丸ごと作り直すコマンドを用意する。

- 投入先: **本番（Render）だけ**
- 消す範囲: **自分の管理者アカウント（superuser/staff）以外すべて**。聖書本文（CanonicalBook / Book / Chapter / Verse）は消さない
- コマンド: `seed` と `seed_en` を廃止し、**`seed_demo` に一本化**
- 規模: **特大**（一覧が何ページも続き、全機能・全状態が埋まる量）

---

## 1. 今どうなっているか（前提の確認）

読んで分かったこと。

| 機能 | 今のシード | 問題 |
|---|---|---|
| コメント | あり（数百件） | 量が足りない。深い返信・削除・通報の件数も少ない |
| Q&A | 5件（seed）/ 7件（seed_en） | 1ページにも満たない。ページ送りが確認できない |
| 記事 | **ゼロ** | 一覧・タグ絞り込み・引用表示・記事コメントが未確認のまま |
| プラン | **ゼロ** | 一覧・日程・購読・進捗が未確認のまま |
| 翻訳プロジェクト | 3〜4件 | 状態の組み合わせが埋まっていない。本棚（/read に追加）が未投入 |
| お気に入り（栞） | 節栞とコメント栞のみ | 書栞・章栞・**翻訳プロジェクト栞**が未投入 |
| 通知 | reply / upvote のみ | mention と、Q&A の回答通知が無い |

一覧はすべて **1ページ 20件**（`common/pagination.py`）。ページ送りを何度も試すには、1つの一覧で最低でも 300件以上ほしい。

ローカルの聖書データは 96書 / 189版（口語訳・KJV・TR(GRC)・LXX英訳・トマス福音書・エノク書ほか）。
**本番に何が入っているかは分からないので、コマンドは書名を決め打ちせず、DB にある書を実際に読み取って使う。**

## 2. 作るもの

### 2-1. 新コマンド `python manage.py seed_demo`

```
python manage.py seed_demo --wipe --scale xl
```

| オプション | 意味 |
|---|---|
| `--wipe` | 既存データを消してから投入する。**付けないと消さない**（本番での事故防止のため既定は消さない） |
| `--scale` | `small` / `large` / `xl`（既定 `xl`）。small は開発コンテナ起動時の自動投入用 |
| `--admin-username` | 「使い込んだ状態」にする管理者。省略時はいちばん古い superuser を自動で選ぶ |
| `--seed` | 乱数の種（既定 20260802）。同じ種なら毎回同じデータができる |

### 2-2. 消す順番（`--wipe`）

外部キーの依存順に消す。聖書本文とタグ定義は残す。

```
通知 → プラン進捗 → プラン購読 → プランの読む章 → プランの日 → プラン
→ 記事コメント → 記事の引用索引 → 記事
→ Q&A 回答 → Q&A 質問 → 通報 → 投票 → 栞 → コメント → 読書進捗
→ 翻訳コメント → 翻訳本棚 → 翻訳ユニット → 翻訳メンバー → 翻訳プロジェクト
→ ユーザー（superuser / staff 以外すべて）
```

残すもの: 聖書本文、`ArticleTag`（マイグレーションで入る 15 個）、`Tag`（コメント用 5 個）、`Language`（10 言語）、管理者アカウント。

### 2-3. 日時をばらけさせる

`created_at` は自動で「今」が入る仕様なので、そのままだと全部が同時刻になり、一覧が不自然になる。
`bulk_create` のあとに `bulk_update` で **過去 18 か月に分散**させる。最近ほど密にして、新しい投稿が上に来るようにする。

## 3. 投入する量（特大）

### ユーザー: 220人

- 日本語圏 110人 / 英語圏 110人。名前・自己紹介ともそれぞれの言語で書く
- 自己紹介は「牧師・神学生・看護師・エンジニア・翻訳者・求道中」など職業と背景を組み合わせて全員違う文面にする
- 自己紹介が空の人、`bookmarks_visibility` が public の人 / private の人を混ぜる
- パスワードは全員 `Seed@pass123`（従来どおり。ログインして挙動を見るため）

### コメント: 約 25,000件

| 種類 | 量 | 狙い |
|---|---|---|
| 節コメント | 1,200箇所 × 3〜25件 | 節ごとの多寡の差を出す。20件超の節を多数作る |
| 章コメント | 40章 × 30〜80件 | 章タブのページ送りを何ページも試せる |
| 書コメント | 60書 × 2〜10件 | 書のトップの表示 |
| 返信ツリー | 最大 **深さ5** | 深いネストの折りたたみ・インデント確認 |
| 論理削除 | 200件 | 「削除されました」表示。子の返信は残る |
| 翻訳プロジェクト向けコメント | 1,500件 | 聖書本体と分離されているかの確認 |

- タグ（感想・解説・証し・祈り・考察）を 6割に付与
- 日本語コメントと英語コメントを混在させる（同じ節に日英が並ぶ状態を作る）
- 文面は言語ごとに 120種の下敷きを用意し、書名・章節・語彙を差し込んで見た目の重複を減らす

### 投票: 約 120,000件

上位 8,000コメントに 1〜60票。人気コメントと 0票コメントの差を作り、並び順の違いを見えるようにする。

### Q&A: 質問 400件 / 回答 約 2,500件

- 未解決 200件・解決済み 200件（**どちらの列も 10ページ分**）
- 粒度は 書 / 章 / 節 の3種すべて
- 回答 0件の質問、回答 1件、回答 15件、**回答 80件の質問を1つ**（回答一覧のページ送り確認用）
- タグ付き / タグ無し、日本語質問 / 英語質問を混在
- 質問・回答それぞれに通報を付ける（管理画面の確認用）

### 記事: 400件

| 公開状態 | 件数 |
|---|---|
| 公開 | 320件（一覧 16ページ） |
| 限定公開 | 40件 |
| 下書き | 40件（うち一部は管理者のもの） |

- 主題タグ 15種すべてを使い、1記事 1〜3個。タグ絞り込み後も複数ページになる分量にする
- 本文は Markdown。見出し・箇条書き・引用・強調・リンクを含める
- **引用の印は全パターンを網羅**
  - `[[matthew 6:16]]` 1節の文中参照
  - `[[matthew 6:16-18]]` 範囲の文中参照
  - `[[matthew 6]]` 章まるごとの参照
  - `{{john 3:16}}` 引用ブロック
  - `{{john 3:16|KJV}}` 訳を指定した引用ブロック
  - `[[enoch 1:1]]` 外典への引用
  - `[[notabook 1:1]]` **存在しない書**（「見つかりません」表示の確認）
  - 1記事に 15個以上の引用を入れたものを数本
- 本文が短い記事・長い記事（1万字級）を混ぜる
- 記事コメント: 合計 3,000件。返信ネストあり、論理削除あり、**1記事に 120件付けたもの**（6ページ分）

### プラン: 120件

| 公開状態 | 件数 |
|---|---|
| 公開 | 90件 |
| 限定公開 | 15件 |
| 下書き | 15件 |

- 日数のばらつき: 3日 / 7日 / 14日 / 21日 / 30日 / 60日 / 90日 / **365日を1本**（上限の確認）
- 1日に読む章は 1〜10章（上限 10 の確認）
- **正典と外典をまたぐ並び**（創世記 → エノク書 → トマス福音書）を必ず入れる
- 訳を指定した日（あえてギリシャ語で読ませる日）を入れる
- 日ごとの題・devotional（数百字の文章）を書く。題も文章も空の日も混ぜる
- 訂正メモ（note）が入ったプランを作る
- 購読: 人気プランは 40人、不人気は 0人。**読者ゼロのプラン**を残す（日の並べ替えができる状態の確認用）
- 進捗: 未着手 / 途中 / 完走 / やめた（is_active=false）を混ぜる

### 翻訳プロジェクト: 40件

- 状態 draft 10 / active 15 / published 15
- 対象言語は 10言語すべてを使う
- メンバー: 承認済み 3〜15人、承認待ち 0〜8人、拒否 0〜3人
- ユニット: プロジェクトごとに 50〜300節。todo / in_progress / review / done の4状態をすべて含む。担当者あり / なし
- 議論コメント: プロジェクト全体宛 25件以上（ページ送り確認）＋ユニット別コメント
- **本棚（TranslationLibraryEntry）**: 公開プロジェクトを 5〜60人が /read に追加した状態にする

### お気に入り（栞）: 約 6,000件

**5種類すべて**を入れる。

1. 書栞（書だけ）
2. 章栞（書＋章）
3. 節栞（書＋章＋節）
4. コメント栞
5. **翻訳プロジェクト栞**

1人あたり 10〜60件。管理者アカブントには 5種すべてを合計 80件以上（栞一覧が 4ページ以上になる）。

### 読書進捗: 約 4,000件

1人 5〜40書。最終読書日時をばらけさせ、/read の「読みかけ」の並びを確認できるようにする。

### 通知: 約 15,000件

- 種類: reply / upvote / mention の3種すべて
- **Q&A の回答通知**（answer 参照）も入れる
- 翻訳コメントの通知も入れる
- 既読・未読を混在。管理者宛に 150件以上（未読タブ・全件タブとも複数ページ）

### 通報: 300件

コメント / 質問 / 回答の3対象、理由4種（spam / offensive / misinformation / other）すべて。

### 管理者アカウントの状態

「自分でログインして全機能を触れる」状態にする。

- 自分の記事: 公開 5本 / 限定公開 2本 / 下書き 3本
- 自分のプラン: 公開 3本 / 下書き 2本（うち1本は読者あり、1本は読者ゼロ）
- 購読中のプラン 5本（進捗が途中のもの・完走したもの）
- 所有する翻訳プロジェクト 2本＋参加中 3本＋承認待ち 1本
- 栞 80件以上（5種すべて）
- 通知 150件以上（未読多数）
- コメント 50件、質問 10件、回答 30件

## 4. 作業の進め方

| 段階 | 内容 |
|---|---|
| 1 | `backend/common/management/commands/seed_demo.py` を新規作成。文章の素材は `seed_data/`（ja.py / en.py）に分けて置く |
| 2 | 削除処理・日時ばらし・一括投入の土台を作る |
| 3 | ユーザー → コメント・投票 → Q&A の順に投入処理を書く |
| 4 | 記事（引用の全パターン）・プランを書く |
| 5 | 翻訳プロジェクト・栞・進捗・通知・通報を書く |
| 6 | `seed` / `seed_en` を削除し、`docker-entrypoint.sh` を `seed_demo --scale small` に差し替える |
| 7 | テスト（`backend/tests/test_seed_demo.py`）: small スケールで実際に走らせ、各テーブルの件数と、制約違反が起きないことを確認 |
| 8 | ローカル Docker で `--wipe --scale xl` を1回流し、画面を目視確認（所要時間・DB サイズも測る） |
| 9 | push → PR → マージ → デプロイ |
| 10 | Render のシェルで `python manage.py seed_demo --wipe --scale xl` を実行（手順は別途案内する） |

### 段階8について

投入先は本番だけという指示だが、**いきなり本番で流す前にローカルで1回試させてほしい**。
理由は、途中で落ちると本番のデータが消えただけの状態で止まるため。ローカルの Docker のデータは開発用なので消えて困らないはず。
（ローカルも触ってほしくない場合は言ってほしい。その場合はテスト（段階7）だけで判断して本番に流す）

## 5. 気をつける点

- **本番の聖書データに合わせる**: 書名・訳名を決め打ちせず、DB から実際に引いて使う。無い書は黙って飛ばす
- **メモリと時間**: 全部を1つのトランザクションに入れると重いので、機能ごとに区切ってコミットする。1,000件ずつ `bulk_create` する
- **消し忘れ防止**: `--wipe` を付けたときだけ消す。付け忘れると二重投入になるので、既存データが残っていたら警告を出す
- **DB 容量**: 特大だと 概算 150〜250MB 増える見込み。Render のプランの上限を段階8で実測してから流す
- **再現性**: 乱数の種を固定するので、同じコマンドなら同じデータができる

## 7. 実装したときの記録

### 決めたこと

- **管理者は自動で用意する**。superuser が既にあればそれを使い、無ければ `admin` を作ってパスワードを1回だけ表示する。ユーザー名の指定は不要（`--admin-username` で変えられる）
- **パスワードは毎回自動生成**して最後に表示する。本番に 220 人分の既知のパスワードを置きたくないため、`Seed@pass123` の固定値は廃止した
- **二重投入を拒否する**。`--wipe` なしでデータがある DB に流すとエラーで止まる（量が読めなくなるのを防ぐ）

### 作ったファイル

| ファイル | 役割 |
|---|---|
| `backend/common/management/commands/seed_demo.py` | コマンド本体 |
| `backend/common/seed_data/ja.py` / `en.py` | 文章の素材（完成品ではなく短い文の束） |
| `backend/tests/test_seed_demo.py` | small 規模で実際に流して確かめるテスト |

文章は「1〜3 文を選んで組み合わせる」方式にした。数百の素材から数万通りの本文ができるので、
一覧を眺めても同じ文章が並ばない。

### つまずいた点

- **作成日時**: `auto_now_add` は代入を無視するので、`bulk_create` のあとに `bulk_update` で日時を上書きする形にした（`bulk_update` は自動更新を通らない）
- **タグの中間テーブル**: 記事タグの列名は `tag_id` ではなく `articletag_id` だった
- **`random.sample`**: 削除済みを除いた母集団より多く取ろうとして落ちた。件数は必ず母集団側から取る

### 削除・差し替え

- `seed` / `seed_en` を削除
- `docker-entrypoint.sh` は `seed_demo --scale small` に差し替え。判定も「シードユーザーの有無」から「コメントの有無」に変更
- README のシードの節を書き直し
