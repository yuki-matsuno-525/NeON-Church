# デザインリファクタリング（決定版）

このドキュメントは「見た目の書き方」の決定を記録するものです。
以後、フロントエンドで見た目に関わるコードを書くときは、必ずここのルールに従います。

## なぜやるのか

サイト全体がなんとなく素人っぽく見える原因を調べた結果、デザインのセンスの問題ではなく、
**「見た目をどこにどう書くか」が決まっていなかったこと**が原因だと分かりました。

調査時点（2026-08-03）の実態:

| 書き方 | 使用量 | 状態 |
| --- | --- | --- |
| インライン `style={{ }}` | 1,147 箇所 / 84 ファイル | 事実上これが本体 |
| globals.css の共通クラス | 584 行あるが `.btn` 20 回、`.card` 1 回 | 作ったが使われていない |
| CSS Modules | 2 ファイルのみ | ほぼ未使用 |
| Tailwind | **使用 0 箇所** | 設定は完了しているのに一度も使われていない |

書き方が決まっていないので、画面を作るたびに一番手軽なインラインが選ばれ続けました。
インラインは再利用できないため、同じ見た目を毎回書き直すことになり、値がばらけました。

その結果:

- 文字サイズが **16 種類**（10,11,12,13,14,15,16,17,18,20,22,24,26,28,30,64）
- 余白が **19 種類**（2,3,4,5,6,8,10,12,14,16,18,20,24,28,32,36,40,52 …）
- 角丸が **11 種類**、文字の太さが **5 種類**
- 一番多い文字サイズは 13px（171 回）だが、これは既存の設計表に存在しない値

さらに、インラインは後から CSS で上書きできないため、`globals.css` が `!important` に頼る状態になっていました。
（該当箇所のコメント: 「画面ごとの指定（インラインの style）に勝つ必要があるため `!important` を付けている」）

## 決定 1: 使う値を絞る

| 項目 | 段数 | 値 |
| --- | --- | --- |
| 文字サイズ | 6 | 12 / 14 / 16 / 20 / 28 / 40（ヒーローのみ） |
| 文字の太さ | 2 | 400 / 700 |
| 余白 | 7 | 4 / 8 / 12 / 16 / 24 / 32 / 48 |
| 角丸 | 4 | 4 / 8 / 12 / 999 |

### 既存の値の寄せ先

- 文字: 10,11 → 12 ／ **13,15 → 14** ／ 17 → 16 ／ 18,22 → 20 ／ 24,26,30 → 28 ／ 64 → 40
- 太さ: 500,600,800 → 700
- 余白: 2,3,5 → 4 ／ 6 → 8 ／ 10,14 → 12 ／ 18,20 → 16 ／ 28 → 24 ／ 36,40 → 32 ／ 52 → 48
- 角丸: 3,5,6 → 4 ／ 10 → 8 ／ 14,16,20 → 12

13px（171 箇所）は一律 14px に上げます。全体がわずかに大きく・読みやすくなります。

### 補足: 基準サイズを 14px から 16px へ

`globals.css` の `body { font-size: 14px }` がサイト全体の基準でした。
これが「全部小さい」の大元なので、16px に引き上げます。

## 決定 2: Tailwind 中心で書く

Next.js 16 の公式ドキュメント（`node_modules/next/dist/docs/01-app/01-getting-started/11-css.md`）の推奨に従います。

> グローバル CSS は本当に全体に効くものだけに使い、コンポーネントのスタイルは Tailwind CSS、
> Tailwind で足りないところだけ CSS Modules を使うことを推奨します。

このプロジェクトは Tailwind の設置がすでに完了しています（`tailwindcss` 4.2.4 と
`@tailwindcss/postcss` が入り、`postcss.config.mjs` も `@import "tailwindcss"` も書かれている）。
使われていないだけなので、追加の導入作業はありません。

### 何をどこに書くか

| 何を | どこに書くか |
| --- | --- |
| 余白・文字サイズ・並べ方・色 | **Tailwind のクラス** |
| ネオンの光・ガラス・グラデーション | globals.css の共通クラス（`.card-glow` など既存のもの） |
| Tailwind で書きにくい画面固有のもの | その画面の `.module.css` |
| JavaScript で計算する値（進捗バーの幅など） | インライン（**ここだけ残す**） |

現在うまくいっている部分（ネオンの世界観）はそのまま残し、
壊れている部分（余白と文字サイズのばらつき）だけを Tailwind に任せます。

なお、インライン 1,147 箇所のうち、本当に計算が必要なものは **3 箇所だけ**でした。
残りはすべて固定値なので、機械的に置き換えられます。

### なぜ Tailwind だと値が揃うのか

決めた表を Tailwind の `@theme` に登録すると、**クラス名がその表そのものになります**。
表にない値はクラスが生成されないため、書いても効きません。

実際に導入済みの Tailwind 4.2.4 でコンパイルして確認した結果:

| 書いたクラス | 結果 |
| --- | --- |
| `p-1` `p-2` `p-4`（表にある） | 生成される |
| `p-3` `p-5`（表にない） | **生成されない** |
| `text-sm` `text-md`（表にある） | 生成される |
| `text-lg`（表から外した） | **生成されない** |
| `text-red-500`（Tailwind 標準色） | **生成されない** |

「気をつけて揃える」という運用努力ではなく、仕組みとして値が揃います。
決定 1 と決定 2 が、ひとつの作業として同時に達成されます。

## 進め方

| # | やること | 見た目の変化 |
| --- | --- | --- |
| 1 | このドキュメントを書く | なし |
| 2 | `@theme` に値の表と色を登録する | **なし**（クラスが使えるようになるだけ） |
| 3 | 基準の文字サイズを 14px → 16px にする | あり（全体が読みやすくなる） |
| 4 | 共通部品（Button / Card / Badge / TextField）を Tailwind で作り直す | 小 |
| 5 | 各画面のインラインを Tailwind へ移す（多い順） | 画面ごとに確認 |
| 6 | `!important` 撤去・残インライン検査・テスト・PR | なし |

各段階で http://localhost:3000 を目視確認しながら進めます。

### 移行の優先順位（インラインが多い順）

```
app/translations/[id]/page.tsx        107
app/page.tsx                           39
app/articles/[id]/edit/page.tsx        38
components/comments/CommentItem.tsx    37
components/articles/CitationPanel.tsx  36
app/profile/page.tsx                   36
app/search/page.tsx                    34
app/read/page.tsx                      33
components/reader/CommentPanel.tsx     31
（以下、合計 84 ファイル）
```

ただし実際は **4（共通部品）を先に済ませます**。生の `<button>` が 167 箇所あり、
これを共通部品に寄せるだけで各画面のインラインが大きく減るためです。

## このドキュメントの使い方

新しく画面やコンポーネントを作るときは、

1. 上の「何をどこに書くか」の表に従って書く場所を決める
2. 値は決定 1 の表から選ぶ（表にない値は Tailwind が受け付けません）
3. 迷ったら既存の共通部品（`components/ui/`）を探す。無ければ作って共有する

を守ってください。
